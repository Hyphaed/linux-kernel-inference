## What it changes

Adds one field to `struct dma_buf` (`atomic_t priority`, default `128` of a
`0`-`255` range), two kernel-internal accessors (`dma_buf_set_priority()` /
`dma_buf_get_priority()`, `EXPORT_SYMBOL_NS_GPL` in namespace `DMA_BUF`), two
new ioctls (`DMA_BUF_IOCTL_SET_PRIORITY` / `_GET_PRIORITY`, the next free
slots after the existing sync-file ioctls), and one new `fdinfo` line. No
existing `dma_buf_ops` callback, field, or ioctl is touched, renamed, or
resized.

## Why

`dma-buf` has no generic way for an exporter, importer, or userspace to hint
how eagerly a given buffer's backing memory should give way under pressure.
Pages pinned via `pin_user_pages()`/`FOLL_LONGTERM` sit outside normal
reclaim by design, so there's no shared answer today to "if something has to
give, give up *this* one first." Confirmed by grep before drafting: no
existing priority/shrink/reclaim hook on `struct dma_buf_ops` or `struct
dma_buf`.

Not a GreenBoost-only benefit — `dma-buf` is generic to Linux, used by video
capture cards, compositors, multi-GPU renderers, VR/AR pipelines, and any
other AI/ML tiering stack. See the README's "In plain English" and "Who this
could help — not just GreenBoost" sections for the non-engineer explanation
and the full list of other beneficiaries.

**Concrete motivating case, not hypothetical:** GreenBoost's `greenboost.c`
(a sibling project on this machine) re-implemented exactly this — a
`gaming_mode` sysfs flag plus a private per-buffer "heat" score and a private
`GB_IOCTL_GAMING_MODE` ioctl, purely because there was nowhere generic to say
it. As of the 2026-07-26 Speed Program audit, GreenBoost's
`gb_apply_priority_hint()` now actually calls
`dma_buf_set_priority(dmabuf, 200)` at all three `dma_buf_export()` sites for
KV-cache/T1-priority buffers — a real, working consumer, not the speculative
example this RFC originally shipped with.
