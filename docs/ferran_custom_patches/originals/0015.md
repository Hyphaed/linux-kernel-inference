# 0015 — nvme: lower default APST max latency for desktop/workstation use

**File:** `patches/0015-nvme-lower-default-apst-latency.patch`
**Touches:** `drivers/nvme/host/core.c`, 1 line changed
**Authored as:** `hyphaed workstation tuning <noreply@local>`

## What it changes

Lowers the compiled-in default of `default_ps_max_latency_us` from `100000`
(100ms) to `25000` (25ms). This bounds how deep an NVMe drive's Autonomous
Power State Transition (APST) is allowed to go by default — deeper power
states save more idle watts but cost more wake latency on the next access.

## Why

This workstation stages AI model weights and GreenBoost T2/T3 tiering data
from NVMe (CUDA pinned-memory staging, mmap'd checkpoint loads). A 100ms wake
spike on a cold random read is directly visible as an inference stall. 25ms
still allows APST into shallow power-saving states — idle power draw still
drops — but bounds worst-case wake latency to something that shouldn't show
up as a stutter under load.

## Verification

Compile-scope only (single `static unsigned long` initializer change,
mechanically low-risk). No before/after latency measurement is recorded in
this tree.

## Upstream readiness: keep local, do not send as-is

This changes a *default* that ships to every kernel using it, not a
workstation-scoped knob. Upstream reliably wants broad cross-workload data
before moving a shared default — a single machine's staging-load anecdote
isn't that. See `../proposals.md` for the reshape suggestion (a Kconfig knob
or a documented workstation preset, not a default flip) before this is worth
sending.

The value is already runtime-overridable without a kernel patch at all:
```
echo 25000 > /sys/module/nvme_core/parameters/default_ps_max_latency_us
```
or via `nvme_core.default_ps_max_latency_us=25000` on the kernel cmdline —
worth using that instead of carrying a forward-ported patch, unless the
compiled-in default specifically matters for some other reason.
