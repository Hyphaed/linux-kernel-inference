## What it changes

Adds one field to `struct dma_buf` (`struct dma_buf_compression_hint
compression` — `{codec, block_size, uncompressed_size}`, defaulting to
`DMA_BUF_CODEC_NONE` via the existing `kzalloc()` in `dma_buf_export()`) and
a dedicated `compression_lock` spinlock guarding it, two kernel-internal
accessors (`dma_buf_set_compression()` / `dma_buf_get_compression()`,
`EXPORT_SYMBOL_NS_GPL` in namespace `DMA_BUF`, same namespace `0019` uses),
two new ioctls (`DMA_BUF_IOCTL_SET_COMPRESSION` / `_GET_COMPRESSION`,
numbered 6/7 since `0019` already claims 4/5), and one new `fdinfo` line
(omitted when the buffer is uncompressed). No existing `dma_buf_ops`
callback, field, or ioctl is touched, renamed, or resized.

**Why a dedicated lock instead of the `atomic_t` pattern `0019` uses:** the
descriptor is three fields that must be read back as a consistent group — a
torn read could pair one codec's `block_size` with a different codec's
`uncompressed_size`. `0019`'s single-field priority hint doesn't have that
failure mode, so it correctly didn't need one.

## Why

Same shape of gap as `0019`, one level further along the same idea. `0019`
lets an exporter say *which* buffers to keep under memory pressure; this
patch lets an exporter that has *chosen* to keep a buffer say "compressed,
not evicted" — so an importer promoting it back knows to inflate it locally
instead of assuming a full re-fetch over the host↔device interconnect is
needed. Confirmed by grep before drafting: no existing compression/codec
descriptor on `struct dma_buf_ops` or `struct dma_buf`.

Not GreenBoost-specific — the same generic dma-buf mechanism used by V4L2
compressed capture, DRM/KMS framebuffer compression, and any other
memory-tiering system has this identical gap today. `@codec` is deliberately
opaque (kernel does not interpret it, exporter/importer agree by
convention), the same pattern `DRM_FORMAT_MODIFIER` and V4L2 fourccs use —
this patch defines no codec IDs beyond `DMA_BUF_CODEC_NONE` (0); a shared
registry is a follow-up once real out-of-tree users exist to agree on one.

**Concrete motivating case:** GreenBoost's `gb_moe.py` demotes cold MoE
experts to save VRAM. As of this session it was doing so via
`gb_quant.quantize_module(..., int4)` — lossy, and an expert promoted back
returns int4-degraded. Replacing that with a lossless codec (tracked
separately) and publishing the result through this descriptor at the same
three `dma_buf_export()` sites `0019`'s priority hint already touches in
`greenboost.c` turns "evicted, re-fetch on demand" into "compressed
in-place, decompress locally" — for an *immutable* buffer (model weights
don't change mid-session), that is strictly better than any refetch, at any
compression ratio, because it eliminates the transfer entirely rather than
shrinking it.
