# 0016 — mm: default THP defrag to defer+madvise instead of madvise

**File:** `patches/0016-mm-thp-defrag-defer-madvise-default.patch`
**Touches:** `mm/huge_memory.c`, 1 line changed
**Authored as:** `hyphaed workstation tuning <noreply@local>`

## What it changes

Swaps the unconditional default-flags initializer for transparent hugepage
(THP) defrag from `TRANSPARENT_HUGEPAGE_DEFRAG_REQ_MADV_FLAG` ("madvise" mode)
to `TRANSPARENT_HUGEPAGE_DEFRAG_KSWAPD_OR_MADV_FLAG` ("defer+madvise" mode).

## Why

The kernel always initializes defrag to "madvise" mode regardless of the
`CONFIG_TRANSPARENT_HUGEPAGE_ALWAYS`/`MADVISE` Kconfig choice that controls
*whether* THP is used at all. "madvise" defrag mode runs synchronous
compaction directly in the page-fault path for `MADV_HUGEPAGE`-tagged VMAs —
fine when `transparent_hugepage=madvise`, but this workstation's AI-only
preset switches to `transparent_hugepage=always` (CUDA pinned host buffers,
GreenBoost T2 staging), so every anonymous fault becomes THP-eligible and can
hit synchronous compaction stalls under memory pressure from concurrent
inference + gaming + VMs.

"defer+madvise" keeps the same allocation behavior but pushes compaction work
to `khugepaged`/`kswapd` in the background instead of stalling the faulting
thread — this matches long-standing guidance for other `THP=always` workloads
(Redis, MongoDB) that hit the same synchronous-compaction-stall problem.

## Verification

Compile-scope only (single flag-bit initializer change). No before/after
stall measurement is recorded in this tree.

## Upstream readiness: keep local, do not send as-is

Same category as `0015`: a default-behavior change, not a bug fix, and
upstream wants broad data before moving a shared default rather than one
workstation's workload profile. See `../proposals.md`.

Already runtime-overridable without a kernel patch:
```
echo defer+madvise > /sys/kernel/mm/transparent_hugepage/defrag
```
Prefer setting this at boot/service-start time over carrying a forward-ported
default-flag patch, unless the compiled-in default specifically matters (e.g.
for a window before userspace init runs).
