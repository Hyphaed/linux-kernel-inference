# 7.2.9 patch sweep, 2026-10-04

This is the first sweep run through `scripts/bump/` instead of by hand, so most of
what's here is a record of what the scripts found, plus the calls made on it.
Reproduce with `make bump VER=7.2.9 SWEEP_ONLY=1`; raw output lands in
`out/sweep/7.2.9/` (`sources.txt`, `inventory.md`, `candidates.md`).

## The source list is now a file, and every URL in it was checked

`patches/sources.tsv` holds 40 sources: name, URL, branch, kernel version, type,
which hardware it needs, and whether to clone it or only verify it. Each URL
answered `git ls-remote` on 2026-10-04. `make sources-check` re-runs that.

Three URLs I'd have guessed were wrong, which is why none are guessed:

* `axboe/linux-block.git` doesn't exist on kernel.org. The block/io_uring tree is
  `axboe/linux.git`, and that's what's listed.
* The NVMe tree at `git.infradead.org/nvme.git` doesn't speak git over https
  (`could not determine hash algorithm`). Dropped rather than listed unverified.
* Valve's `ValveSoftware/steamos_kernel` is real but stale: its newest branch is
  `brewmaster-4.11`. Current Valve work is `evlaV/linux-integration`, which the
  sync already pulls. Kept in the file as `ls`-only, marked STALE.

Sources whose hardware this machine doesn't have are verified but never cloned or
ranked: `drm-i915` and `drm-xe` (the 14900KF has no iGPU), `amdgpu-staging`,
`thunderbolt`, `mellanox`, and the three ARM trees. Eight rows are skipped that way
and `inventory.md` says so per row. Twelve carriers are cloned blobless and shallow
into `github/sources/` (zen, liquorix, gentoo, sirlucjan, graysky, community
patches, BORE upstream, xanmod-patches, clear, arch, debian, ubuntu).

`graysky-compiler` stays in as a candidate source but the 7.2.8 sweep already ruled
on it: `CONFIG_X86_NATIVE_CPU=y` beats the generic ISA-level patches.

## What the sweep found, and what was done about it

**Taken: nothing new from outside.** Same result as 7.2.8, and for the same reason:
the evidence rule for a carried patch is that it fixes something observable on this
box or comes from a maintained fork's native 7.2 pin, and nothing in this pass
qualified.

* **BORE.** `firelzrd/bore-scheduler` published `BORE 7.0.0 (testing)` for 7.2.
  It's a new major version labelled testing, and CachyOS hasn't moved its 7.2
  `sched/` directory off the BORE we already carry (its three newest commits there
  are muqss). Not taking a testing scheduler on a desktop daily driver. 7.2.9
  touched `kernel/sched/{core,fair}.c` and `include/linux/sched.h`; BORE still
  applies clean. Revisit when 7.0.0 loses the "testing" label or CachyOS ships it.
* **Clear Linux "powerbump".** An NVMe power-state patch set last touched June 2025,
  from an Intel author, with no measurements in the commit. Our 0013 already lowers the APST latency on
  this DRAM-less Samsung PM9C1a. Not adopted.
* **Zen, Liquorix, sirlucjan, Gentoo, community-patches.** The commits that survived the keyword filter
  are stable-release backports (already in 7.2.9), old-kernel tkg patches, or RT/schedutil
  config choices we don't need; I read the ranked list, not every commit. `inventory.md` tags those `[already carried]` / `[dup of ...]`.
* **v7.2..v7.3-rc5 window.** 489 fix-subject commits in the paths this box
  exercises. The `sched/cache` and `sched_ext` items are for features 7.2 doesn't
  have; the PAT/MCE/mm/io_uring fixes carry `Cc: stable` and are showing up in
  `stable-queue/queue-7.2` (28+ patches queued for 7.2.10). Waiting for stable is
  cheaper than carrying them and costs nothing here.
* **Ubuntu SAUCE.** Not re-downloaded; it was empty on 7.2.8 and the package version
  hasn't changed.

**Kconfig changes between 7.2.8 and 7.2.9: none.** So no fragment needs a decision
this bump, and `50-config-audit.py` is only checking that existing lines still land.

## What did change, and why

* **0030 is now in the series** (`PCI: skip the 2.5GT/s restriction lift on a root
  port with no link`). `00:1c.0` is an empty root port that spends the full 1000 ms
  `PCIE_LINK_RETRAIN_TIMEOUT_MS` on every boot waiting for a link that can't come up,
  then logs `retraining failed`. Still reproduces on the running 7.2.8. The subject
  says `[RFC PATCH]` because there's no before/after timing yet; the 7.2.9 boot is
  that measurement.
* **0029 is now v2.** sashiko's review of the RFC was right: `num_online_nodes() == 1`
  rewrites a `_PXM` naming an offline node to node 0, because the `node_online()`
  check above it has already turned that into `NUMA_NO_NODE`. `nr_node_ids == 1`
  can't hit that, since a single possible node has no offline sibling.
* The series is 26 patches. A real sequential `git am --3way` onto v7.2.9 applied all
  26 with no conflicts, and all 32 objects the series touches compile.

## Things the scripts turned up about themselves

* `tests/test_tag_refresh.py::test_the_release_list_includes_dot_zero_releases`
  asked `list-versions` for 8 releases and expected one of them to be `7.2`. With
  7.2.9 out that's nine point releases, so it started failing the moment the mirror
  learned about the tag. It asks for 40 now.
* Compiling `kernel/sched/debug.o` on its own fails with `implicit declaration of
  cpu_clock`. That's not the patches: `debug.c` is included by the sched unity
  builds, so the validator compiles `build_policy.o` and `build_utility.o` instead.
* A parallel `make` of the touched objects died with `fixdep: error opening file
  .acpi.o.d`. Serial passes, so the validator is serial. I didn't establish why the
  parallel run fails, only that it does.
* `tests/kernel_runtime/test_running_kernel_patches.py::test_0004_max_map_count...`
  is red on this host because of a GreenBoost-side `vm.max_map_count` override. It was
  already red before this session; preflight deselects it, and says why in a comment.
