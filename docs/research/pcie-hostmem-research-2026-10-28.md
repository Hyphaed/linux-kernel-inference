# Making host DDR behave like extra VRAM on one RTX 5070 12 GB (Gen4 x16)

Research-only note, 2026-10-28. No measurements were run on this machine; the card was in use. Labels: VERIFIED = source page opened and read (a fetch tool summarised it, so quotes are paraphrase), INFERENCE = my reasoning from verified facts, UNVERIFIED = seen only in a search snippet or a secondary write-up. Anything older than 2025 is marked STALE.

Target: RTX 5070 12 GB (GB205), Gen4 x16 link (about 25 GB/s usable), 16 GB resizable BAR, 64 GB DDR4 dual channel, i9-14900KF, one NUMA node, driver 615.71.09 open modules, CUDA 13.4, Linux 7.2.

## The numbers that frame everything

* Link: about 25 GB/s each way (given by the owner, not re-measured). VRAM bandwidth of a 5070 is roughly 650 GB/s (INFERENCE, spec-sheet figure, not opened). So host memory over PCIe is about 25x slower than VRAM. No technique closes that gap; the job is to keep weights that are touched every token in VRAM and stream only what can be hidden behind compute.
* DDR4 dual channel peaks near 45-50 GB/s (INFERENCE, from DDR4-3200/3600 specs). That is about twice the PCIe link. For MoE decode this means the CPU reading experts in place is faster than shipping the same bytes to the GPU, which is why `--n-cpu-moe` wins for decode and why only a high-hit-rate expert cache beats it.
* Measure first: `nvbandwidth` (github.com/NVIDIA/nvbandwidth, VERIFIED to exist via search listing, not opened) gives host-to-device, device-to-host, bidirectional and copy-engine vs SM-copy numbers in one run.

## What contradicts common assumptions

1. Decode of an expert-offloaded MoE is not PCIe bound. Only the activations cross the link; the limit is CPU plus DDR4 bandwidth (UNVERIFIED claim, supported by arithmetic). Faster link tuning (MPS, ASPM) therefore does almost nothing for decode. It matters for prompt processing and for expert-cache misses.
2. The 16 GB BAR is not a second VRAM path. The window is write-combined, writes are fast, reads are about 20x slower, and the CPU pays for every byte. It exists for latency, not capacity (VERIFIED, GDRCopy README, old hardware).
3. Managed memory and HMM do not behave like extra VRAM on a PCIe card. Access counters are documented for hardware-coherent platforms; a discrete card faults and migrates (VERIFIED, programming guide). The llama.cpp unified-memory switch is reported as inferior to `--fit` (UNVERIFIED).
4. A consumer card likely has one copy engine. Do not design a "bidirectional streaming" scheme on `cudaMemcpyAsync` alone (VERIFIED, one NVIDIA engineer reply).
5. Compression only helps BF16/FP16 data. On Q4/nf4 weights the ratio is near 1 and the decode work costs more than the bytes saved (INFERENCE; ZipServ shows even a 11-bit lossless format loses to FP8 on an RTX 4090).
6. Block size beats everything. vLLM got about 10x from making copies contiguous and megabyte-sized, which is a bigger lever than any PCIe register (VERIFIED, H100, KV data).
7. The Blackwell hardware Decompress Engine is datacenter-only as far as NVIDIA's own post says; do not plan around it on GB205.

## What is new since 2026-01 that a GreenBoost-style stack should adopt

* llama.cpp expert LRU cache (Oct 2026): copy its design, not the code. Upload only misses, small-batch only, size cache about 10% of expert bytes. It validates tiering hot experts in VRAM and leaving cold ones in pinned RAM. Hit-rate counter should be exported to dataflux. (VERIFIED)
* Contiguous-block layout rule from vLLM 0.12 (Jan 2026): store each tiered object as one contiguous span of 1-2 MB or more. (VERIFIED)
* `cudaMemGetLocationInfo` / `cuMemGetLocationInfo` (CUDA 13.4, R615): query where a managed or system-allocated range resides, useful for a tiering daemon to verify placement without guessing. (VERIFIED, release notes). CUDA 13.4 also adds cgroup GPU memory limits, which a tier manager could use to enforce the 10 GB budget (VERIFIED).
* CUDA 13.4 Python `Host` location type with NUMA node selection (UNVERIFIED, secondary summary): irrelevant on one NUMA node.
* Fused-dequant lossless formats (ZipServ, Mar 2026): only for BF16 diffusion weights, after a ratio check. (VERIFIED)
* nvCOMP 5.3/6.0 ANS float8 and float32 modes: only worth a look if the stack ever streams FP8 or FP32 tensors; the GB205 has no hardware engine. (VERIFIED, undated pages)

## Suggested order of measurement (about one hour once the card is free)

1. `nvbandwidth` full run, then `lspci -vvv` link and MPS/MRRS lines: sets the true ceiling.
2. Pinned vs pageable vs mapped vs managed, one 200-line CUDA test (rows 3, 7, 8, 10).
3. Chunk-size sweep with DMA and copy kernel (row 5).
4. `llama-bench` sweep of `--n-cpu-moe` then `--moe-cache-mib` on the MoE model actually served (rows 1, 2).
5. Only then boot-flag A/B (row 13) and compression ratio estimates on a BF16 shard (rows 11, 12).
