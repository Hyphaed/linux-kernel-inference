## Why the trading room's slow passes probably aren't a kernel problem

`~/Dev/investing/docs/room-architecture/pass-latency-live.md` blames "database reads" in `premiums` and `funding_history`. The code says
otherwise (**read**, `invest/ultra/context.py:38`, `:110`): both read **JSON files** (`engine/var/funding/<coin>.json`,
about 600 KB a coin, 6.5 MB in all, plus `underlying_<ticker>.json`), not PostgreSQL. `funding_history` has an
mtime-keyed parse cache, so after a file changes the first pass pays `json.loads` for every coin.

That moves the suspects. 6.5 MB from NVMe is milliseconds even cold; parsing it under load average 9 with
the GIL contended is not. So the levers worth testing are CPU placement and run-queue latency (E-core versus
P-core, other sessions' pytest runs), not page cache and not Postgres tuning. The capture the wizard now takes
measures exactly this: `funding_file_cost` (parse time in a fresh process, repeated, with `fincore` residency),
the `ctx` stage from `ultra_stage_timing`, loadavg, and the root `runqlat`/`offcputime`/`perf sched` traces.
It's an inference until run 1's capture says so: **not measured**.

## `vm.max_map_count`: why GreenBoost's override isn't applied

(**read**) `greenboost_setup.sh:7861` (`cmd_tune_sysctl`) now says `vm.max_map_count` stays "at its current
value", and `tests/installer/test_sysctl_equal.sh:21` asserts the installer doesn't write it. The
supervisor does move other `vm.*` levers at run time (journal 2026-10-12: swappiness 10→5, `watermark_scale_factor`,
`dirty_background_ratio`) but not this one, so nobody sets it, so systemd's `55-map-count.conf` (1048576) wins
and patch 0004's compiled-in INT_MAX default stays masked. The red test's premise was stale, not the system
broken. `test_0004_max_map_count_is_masked_by_the_distro_value` now asserts the real state, and the preflight no
longer deselects it. Whether 1048576 maps is enough for a large model mmap'd under GreenBoost: **not checked**.
