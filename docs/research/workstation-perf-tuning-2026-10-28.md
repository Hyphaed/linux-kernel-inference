# Workstation runtime tuning: research findings, 2026-10-28

Scope: userspace/runtime knobs only, for the i9-14900KF / RTX 5070 / 64 GB box on kernel 7.2.12-hyphaed. Nothing here was applied. Mitigations, Docker bridges, vmnet8 NAT, forwarding and the firewall are out of scope and untouched.

Evidence tags: **[O]** = I opened the page and read it. **[S]** = only seen as a search-result snippet, not opened (weaker, say so before relying on it). **[P]** = probed on this machine today. Anything cited from before 2025 is marked "possibly stale".

## Newly found since 2026-01

* **sched_ext is already running here and nobody listed it.** `hyphaed-scx.service` is enabled and `/sys/kernel/sched_ext/state` says `enabled`, ops `bpfland_1.1.2_x86_64_unknown_linux_gnu` [P]. Installed package `scx 1.1.2-1` (2026-07-03). Upstream is now v1.1.4, published 2026-10-15; v1.1.3 2026-08-19; v1.1.1 2026-05-14 [O: https://api.github.com/repos/sched-ext/scx/releases]. That changes the baseline for every A/B below: "stock EEVDF" is not what this box runs.
* scx_lavd v1.1.4 (2026-10-15) added completion-time-based migration for big.LITTLE (PR #3854) and fixed neighbour migration on non-SMT machines; v1.1.3 added warmth-modulated CPU stickiness. scx_bpfland v1.1.1 (2026-05-14) added "aggressively avoid SMT contention", and v1.1.4 dropped its experimental TIMELY mode [O: same URL]. None of the four release notes names Intel P/E scheduling explicitly; the notes are PR titles only, no numbers.
* CachyOS forum thread, Oct 2025 to Jan 2026: on an Arrow Lake / hybrid Intel desktop, `scx_bpfland -m performance` still favoured E-cores, one poster advised against sched_ext on recent hybrid Intel and to rely on intel_pstate, no benchmark numbers posted, scheduler 1.0.16 (possibly stale vs 1.1.4) [O: https://discuss.cachyos.org/t/how-to-configure-sched-ext-to-prioritize-intel-p-cores/16483]. Anecdote, not measurement.
* llama.cpp v0.7.0, 2026-10-15 [O: https://api.github.com/repos/ggml-org/llama.cpp/releases/latest]: chunked gated-delta-net CUDA kernels, a `GGML_CUDA_GRAPH_DEBUG` option, a CUDA flash-attention race fix. No pinned-memory, mlock or NUMA host-tuning change in the notes. build.md documents `GGML_CUDA_ENABLE_UNIFIED_MEMORY` and `CUDA_SCALE_LAUNCH_QUEUES`; it does not document `GGML_CUDA_NO_PINNED` or `GGML_CUDA_GRAPH_OPT` [O: https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/build.md].
* arXiv 2604.07609 "Blink" (submitted 2026-04-08) [O abstract only]: removes the host CPU from steady-state LLM serving; reports up to 48.6% lower energy per token and that baselines degrade by up to two orders of magnitude under CPU interference. A search snippet said huge pages had negligible effect on vLLM there (2 MB pages cut dTLB misses about 16%, throughput within noise) [S, the abstract page does not contain this, so treat as unverified]. Datacenter serving, not a one-GPU desktop with GreenBoost tiering.
* Phoronix, June 2026: CachyOS with BORE, ananicy-cpp on vs off, no real difference in most benchmarks [S: https://www.phoronix.com/news/CachyOS-Bore-Without-Ananicy].
* intel_pstate: May 2026 patch "Use correct scaling factor on Raptor Lake-E", carried into stable 7.0.11 and 6.18.x [S: https://patchew.org/linux/4523296.ejJDZkT8p0@rafael.j.wysocki/]. It concerns Raptor Lake-E parts with E-cores disabled; not applicable to this 14900KF. No 2026 r8169 regression found; the r8169 bug reports that came up are 2020 to 2023 (possibly stale).
* NVIDIA: could not reach official release notes. A secondary guide mentions 610.43.02 and CUDA 13.3 on Ubuntu 26.04 [S]; the box runs 615.71.09 [P]. Blackwell is open-modules only (NVIDIA README, 595.84 [S]). I found no new module option worth a knob. `nvcc` on this box is CUDA 12.4 [P]; whether that toolkit can target Blackwell (sm_120) is unverified here, check before building CUDA code natively.
* QEMU/libvirt/macOS: Ubuntu ships qemu 10.2.1 [P]. I found no 2026 guidance changing the OSX-KVM recipe; the script still uses `Skylake-Client` plus `ignore_msrs` [S].
* Gaps, stated plainly: no VMware Workstation tuning source was reachable (Broadcom KB URL 404), Ubuntu 26.04 power-profiles-daemon (0.30 installed) / tuned changes were not found, Intel's newest HWP/EPP guidance beyond the kernel doc below was not found, no 2026 lore thread on NVMe/ext4 regressions was found.

## Verdict table

Counts: ADOPT 2, MEASURE-FIRST 16, REJECT 17.

### ADOPT (low risk, evidence adequate)

**A1. `kernel.nmi_watchdog` 1 to 0.** Mechanism: removes the periodic hard-lockup NMI and frees a PMU counter; useful on a box with nohz_full cores and perf/turbostat work. Source: CachyOS-Settings sets it to 0 for the same reason [O: https://raw.githubusercontent.com/CachyOS/CachyOS-Settings/master/usr/lib/sysctl.d/70-cachyos-settings.conf]. Risk: lose hard-lockup detection (kdump-tools is enabled; panics on a real lockup would no longer be triggered by the watchdog). Measure: `sudo perf stat -a -e cycles,instructions -- sleep 10` (counter availability) and `cyclictest -m -p95 -t8 -D 60 -a 4-7` before/after for max latency. Revert: `sudo sysctl -w kernel.nmi_watchdog=1`. Honest note: the only evidence is a distro config and the mechanism; no latency number from this box yet.

**A2. `CUDA_CACHE_MAXSIZE=4294967296` in the inference/FLUX launcher env.** Current default 1 GiB on desktops [O: https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html]. Mechanism: the JIT cache evicts when full, so large PTX-JIT workloads (FLUX/torch kernels compiled on first use) recompile. Risk: up to 4 GiB disk in `~/.nv/ComputeCache`. Measure: run the same FLUX job twice, compare first-run vs second-run wall time, `du -sh ~/.nv/ComputeCache`. Revert: unset the variable. Benefit is unproven on this box; adopt only because cost is zero.

### MEASURE-FIRST

**M1. `intel_pstate/hwp_dynamic_boost` 0 to 1.** Doc: raises the minimum P-state for a short time when a task that was waiting on I/O is scheduled; only in active mode with HWP [O: https://docs.kernel.org/_sources/admin-guide/pm/intel_pstate.rst.txt]. Helps bursty I/O-wait loads (compiles, model load from NVMe). Risk: slightly higher idle power. Measure: `hyperfine -w1 -r5 'cat /opt/models/<file> >/dev/null'` after `echo 3 >drop_caches`, and `turbostat --quiet --show Busy%,Bzy_MHz,PkgWatt -i1`. Revert: `echo 0 | sudo tee /sys/devices/system/cpu/intel_pstate/hwp_dynamic_boost`. Interaction: power-profiles-daemon may rewrite EPP but not this knob.

**M2. EPP `balance_performance` to `performance` (P-cores only, or via `powerprofilesctl set performance` while gaming/streaming).** Doc: EPP is a hint, accepts the strings in `energy_performance_available_preferences` or 0-255 [O: intel_pstate.rst above]. Docs give no desktop recommendation and no numbers. Risk: heat, fan noise, E-core power. Measure: `turbostat` Bzy_MHz and `sudo perf stat`, plus frame time or Moonlight overlay "host processing" for streaming. Revert: `powerprofilesctl set balanced` (ppd owns the file, a direct sysfs write is overwritten on profile change).

**M3. Replace `vm.dirty_ratio=40`/`dirty_background_ratio=10` with absolute `vm.dirty_bytes` / `vm.dirty_background_bytes`.** CachyOS uses 256 MiB / 64 MiB [O: CachyOS sysctl file above]. Mechanism: 40% of 61 GiB lets roughly 20+ GiB of dirty page cache build before writers are throttled, then a large flush hits the NVMe (GreenBoost T3 writes, model copies). Conflicts with your current ratios (setting `*_bytes` zeroes the ratios). Source for the mechanism is the kernel's own behaviour, not a benchmark. Measure: `fio --name=w --rw=write --bs=1M --size=40G --ioengine=libaio --direct=0 --runtime=60` while logging `grep -E 'Dirty|Writeback' /proc/meminfo` and `fio` latency percentiles; compare p99 of a concurrent small read job. Revert: `sudo sysctl -w vm.dirty_bytes=0 vm.dirty_background_bytes=0 vm.dirty_ratio=40 vm.dirty_background_ratio=10`.

**M4. `vm.dirty_writeback_centisecs` 500 to 1500.** CachyOS value [O]. Fewer flusher wakeups. No numbers. Measure with M3. Revert: `sudo sysctl -w vm.dirty_writeback_centisecs=500`.

**M5. NVMe `read_ahead_kb` 4096 to 1024 (or 128 for random).** Only evidence: a RHEL tuning blog suggests about 128 KB random / 2048 KB sequential and says NVMe prefers smaller; blog, anecdotal [S: https://oneuptime.com/blog/post/2026-03-04-tune-nvme-storage-performance-rhel-9/view]. 4096 is probably right for mmap'd GGUF sequential loads; LVM may also carry its own value. Measure: `fio --name=r --filename=/opt/models/x.gguf --rw=read --bs=1M --direct=0` vs `--rw=randread --bs=4k --iodepth=32 --runtime=30`, at both settings, and a real llama.cpp cold load. Revert: `echo 4096 | sudo tee /sys/block/nvme0n1/queue/read_ahead_kb` (also check `/sys/block/dm-0/queue/read_ahead_kb`).

**M6. NVMe scheduler `none` vs `kyber`/`mq-deadline`.** CachyOS udev rules use `kyber` for NVMe [O: .../60-ioschedulers.rules] and `mq-deadline` for SATA SSD. Mixed read-latency under a heavy writer is the only plausible win. Measure: fio mixed job (`--rw=randrw --rwmixread=70`) reading p99 latency under each. Revert: `echo none | sudo tee /sys/block/nvme0n1/queue/scheduler`.

**M7. ext4 `noatime` (and `lazytime`) on `/`.** The ext4 admin guide page I opened does not cover them [O: https://docs.kernel.org/admin-guide/ext4.html]; relatime is already in force so the gain is small. RHEL blog says noatime removes access-time writes [S]. Risk: breaks tools that read atime (mutt, tmpwatch-style cleaners). Measure: `sudo perf stat`/`iostat -x 1` write counts during a `find / -xdev -type f -exec cat {} + >/dev/null` run. Revert: `sudo mount -o remount,relatime /`.

**M8. mTHP: enable a mid size (for example 64 kB) as `inherit`/`always`.** Per-size controls exist and non-PMD sizes default to never [O: https://docs.kernel.org/admin-guide/mm/transhuge.html]. Evidence is mixed: LSFMM 2024 reported about 5% on a kernel compile for 64 kB on 4 kB base pages but a speaker doubted the benefit, and one swap series showed regressions under heavy pressure [S: https://lwn.net/Articles/974826, https://lwn.net/Articles/965120]; all arm64 / 2024 (possibly stale for x86 on 7.2). Measure: `llama-bench` plus `perf stat -e dTLB-load-misses,page-faults`, and watch zram swap-out rates since you use zram 8G. Revert: `echo never | sudo tee /sys/kernel/mm/transparent_hugepage/hugepages-64kB/enabled`.

**M9. khugepaged faster collapse (`scan_sleep_millisecs` 10000 to lower, e.g. 1000).** Doc describes the knobs [O: transhuge.html]; no evidence it matters for LLM weights (which are mostly file-backed `FileHugePages` 940 MB and pinned memory). Measure: `grep -E 'AnonHuge|FileHuge' /proc/meminfo` and `grep thp /proc/vmstat` over a model load. Revert: `echo 10000 | sudo tee /sys/kernel/mm/transparent_hugepage/khugepaged/scan_sleep_millisecs`. Also consider `shmem_enabled` (now never) only if you run tmpfs-heavy work; no evidence.

**M10. GPU power limit below 300 W for decode-only inference.** Several blogs claim single-stream decode is memory-bandwidth bound and a cap of about 2/3 to 80% of max costs little speed [S: blogs, e.g. https://jacquesmattheij.com/llama-energy-efficiency/, ariya.io]; marketing-grade evidence, other cards. Conflicts with `nvidia-gaming-power.service`, which pins 300 W (the max) on purpose for gaming. Use a per-job wrapper, not a global change. Measure: `llama-bench -p 0 -n 128` with `nvidia-smi -pl 300` vs 250, and `nvidia-smi --query-gpu=power.draw,clocks.sm --format=csv -lms 200`. Revert: `sudo nvidia-smi -pl 300`.

**M11. `net.core.netdev_max_backlog` 1000 to 4096.** CachyOS value [O]. On a single 1 GbE NIC probably no effect. Measure first whether drops occur: `awk '{print $2}' /proc/net/softnet_stat` (second column non-zero means backlog drops). If zero, drop it (becomes REJECT). Revert: `sudo sysctl -w net.core.netdev_max_backlog=1000`.

**M12. sched_ext A/B: current bpfland 1.1.2 vs bpfland/lavd 1.1.4 vs no sched_ext (EEVDF).** The only hybrid-Intel evidence is the anecdotal CachyOS thread above (advises against) and the lavd 1.1.4 release notes (big.LITTLE migration work, no numbers). No measured gaming or inference result was found for 14900KF. Mechanism risk: bpfland's primary-domain mask on this CPU is not guaranteed to be the 0-15 P-cores, and your nohz_full/rcu_nocbs/irqaffinity layout assumes particular cores. Measure: `cat /sys/kernel/sched_ext/root/ops`; `sudo journalctl -u hyphaed-scx | grep -i domain`; then `cyclictest -m -p90 -t16 -D 60`, `hyperfine 'llama-bench ...'`, `stress-ng --cpu 32 --metrics -t 30`, and Sunshine frame pacing in the Moonlight overlay under each scheduler. Revert to EEVDF: `sudo systemctl stop hyphaed-scx` (reversible live, sched_ext falls back automatically).

**M13. macOS guest sizing and pinning.** Current script: 4 vCPU, 4 GiB RAM. Pin vCPU threads to P-cores not used by GreenBoost golden cores 4-7 or nohz_full 4-7, for example `taskset -c 8-11` on the qemu process. No source gives a measured gain; the Arch PCI-passthrough page I wanted was blocked (Anubis). QEMU CPU model doc says host-passthrough is the best-feature option when migration isn't needed [O: https://qemu-project.gitlab.io/qemu/system/qemu-cpu-models.html] but OSX-KVM needs `Skylake-Client` for Sequoia/Tahoe, so that stays. Measure: Geekbench/`sysbench cpu` inside the guest and host `perf stat -p <qemu pid>`. Revert: restart without taskset.

**M14. macOS disk: moving `MacHDD` from emulated AHCI/IDE to virtio-blk with an iothread.** QEMU docs: iothreads move block I/O off the main loop, reducing BQL contention and jitter [O: https://www.qemu.org/docs/master/devel/multiple-iothreads.html]. Whether macOS boots from virtio-blk with this OpenCore is unverified here. Measure: guest `diskutil`/`dd` throughput before and after. Revert: restore the `ide-hd` lines.

**M15. systemd service trims.** Enabled and likely unneeded for this workload: `ModemManager`, `cups-browsed`, `avahi-daemon`, `apport`, `kdump-tools` (only if you do not use crash dumps), `nmbd`/`smbd`, `postfix`, `clamav-daemon`, `openvpn`, `cloud-init-*`, `ua-timer`, `motd-news.timer`, `xfs_scrub_all.timer`, `chkrootkit.timer` (a 27.7 s blame entry [P]). No performance source; this is resource hygiene. Do not touch crowdsec, fail2ban, ufw, apparmor, docker, vmware, dnscrypt-proxy. Measure: `systemd-analyze blame`, `ps -eo rss,comm --sort=-rss | head -20`, `systemctl status <unit>` before deciding. Revert: `sudo systemctl enable --now <unit>`.

**M16. Sunshine UDP shaping with `tc` (only if the Shield shows loss).** Sunshine docs: target under 5% loss, jitter under 1 ms, shaping only Sunshine's UDP source port to the client's link speed is the documented advanced fix, not persistent [O: https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2troubleshooting.html]. Not needed when both ends are 1 GbE. Measure: `iperf3 -u -b 900M -t 30` to the Shield, read loss and jitter. Revert: `sudo tc qdisc del dev enp4s0 root` then restore fq_codel via `sudo tc qdisc replace dev enp4s0 root fq_codel`. This touches only egress qdisc on the NIC, not forwarding or the firewall.

### REJECT

* R1 ITMT toggle: debugfs only (`sched_itmt_enabled` permission denied as user [P]); on by default per project notes; no source recommends changing it. The kernel docs I opened do not mention ITMT.
* R2 `nr_requests`: already 1023; a mailing-list user reports lowering it hurt [S]. Keep.
* R3 fstrim / `discard`: timer already active [P]; ext4 doc says discard is off by default pending testing [O]; RHEL blog prefers periodic fstrim [S]. Covered.
* R4 ext4 `commit=`: default 5 s [O]; no evidence for a change.
* R5 ananicy-cpp: not installed; Phoronix June 2026 found no meaningful gaming difference under BORE, and it is untested next to sched_ext, where CachyOS docs warn of conflicts [S]. Skip.
* R6 irqbalance: `irqaffinity=0-3,8-15` plus nohz_full 4-7 is a deliberate static layout; irqbalance would fight it. Reasoning only, no source opened.
* R7 `-cpu host` for the macOS guest: OSX-KVM needs `Skylake-Client`; passthrough on a hybrid P/E part risks guest panics. No evidence for gain.
* R8 static hugetlb pages for QEMU: THP=always already backs guest RAM; no evidence of extra gain; `HugePages_Total 0` stays.
* R9 `kvm halt_poll_ns` / `ignore_msrs`: halt_poll is at the 200000 default, doc calls it a latency vs CPU trade-off with no 2026 numbers [O: https://docs.kernel.org/virt/kvm/halt-polling.html]; ignore_msrs already set in `/etc/modprobe.d/kvm.conf`.
* R10 `GGML_CUDA_ENABLE_UNIFIED_MEMORY=1`: would overlap GreenBoost's own VRAM-to-RAM tiering shim [O: build.md].
* R11 `CUDA_SCALE_LAUNCH_QUEUES` (multi-GPU pipeline only) and `CUDA_DEVICE_MAX_CONNECTIONS` (default 8, single GPU, no evidence) [O: NVIDIA env-var page].
* R12 Lock GPU clocks (`nvidia-smi -lgc`): idle clock 322 MHz is normal; no throttling seen [P]; locking raises idle power and fights the 1-monitor desktop.
* R13 Extra `NVreg_*` options (`EnablePCIERelaxedOrderingMode`, resizable BAR, GSP off): no NVIDIA doc opened recommends them; GSP firmware (`EnableGpuFirmware 1`) is the supported path on Blackwell open modules [S]. `PreserveVideoMemoryAllocations=1` is already set.
* R14 r8169 EEE (unsupported [P]), ring size (already at max 256 [P]), coalescing (`rx-usecs 0`, no adaptive support [P]), disabling offloads: no evidence, would raise CPU cost.
* R15 VMware Workstation tuning: no reachable source (Broadcom KB 404). Nothing proposed rather than guessing.
* R16 `mitigations=off`, forwarding/firewall/bridge changes: forbidden by owner rules.
* R17 cpuidle governor `teo` and `sched_autogroup` changes: kernel cpuidle doc describes teo as an alternative with no benchmark [O: https://docs.kernel.org/admin-guide/pm/cpuidle.html]; autogroup is already 1 and no source favours changing it.

## Conflicts with the existing settings

1. **sched_ext bpfland is live** and not in the "already set" list; every EPP/ITMT/pinning conclusion depends on it (M12).
2. `vm.dirty_ratio=40` on 61 GiB is very large next to CachyOS's 256 MiB (M3).
3. `nvidia-gaming-power.service` pins 300 W; any decode power cap (M10) must be per job.
4. GreenBoost `golden_cpu 4-7` and `nohz_full=4-7` overlap the cores a macOS guest or any pinning would naturally pick; `irqaffinity` excludes 4-7 as well.
5. THP=always plus `shmem_enabled=never` and mTHP sizes off: M8 changes this only with an A/B.
6. `nmi_watchdog=0` (A1) trades away lockup detection while `kdump-tools` is enabled.
