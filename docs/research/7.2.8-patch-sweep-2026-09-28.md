# 7.2.8 patch sweep — upstream v7.3-rc, SteamOS, Ubuntu SAUCE, 2026-09-28

Targeted, upstream-first sweep for the 7.2.8 bump, per the earlier ~270-paper
arXiv sweeps (`platform-kernel-levers-2026-08-31.md`, `topology-levers-`
and `kernel-nvidia-path-2026-09-10.md`) having already produced zero kernel
patches — no reason to re-run that at premier gear again this soon. This
sweep instead mines real code deltas: v7.2..v7.3-rc5 (local mirror,
`github/kernelorg/linux`), Valve's SteamOS kernel (`evlaV/linux-integration`
on GitHub, the official `gitlab.steamos.cloud` remote timed out repeatedly),
and Ubuntu's actual `debian/patches/` for the installed 7.0.0-34.34 source.

## Ubuntu SAUCE — nothing to carry

`python -m patches.eval --against build/linux-7.2.8 --sauce` downloaded the
real Ubuntu 7.0.0-34.34 source package (257 MB, `deb-src` already enabled in
`/etc/apt/sources.list.d/ubuntu.sources`) and reports: **no patches found in
Ubuntu source debian/patches/.** Ubuntu's current cycle ships this kernel
effectively vanilla — no SAUCE to forward-port, confirming the project's
"kernel-org is the sole source" decision needs no revisiting. Nothing to do
here; this is a negative result worth recording so the next bump doesn't
re-run the same 250 MB download expecting a different answer.

## v7.2..v7.3-rc5 — real candidates

Full commit counts by subsystem path are in the session's tool history; the
items below are the ones that survive contact with this box's actual
config/hardware.

**Take (drafted as patch 0031, not yet in series):**

- `eaece4849991 x86/itmt: Don't make ITMT enablement depend on debugfs` —
  `sched_set_itmt_support()` currently treats a debugfs file-create failure
  as fatal, silently disabling ITMT when `CONFIG_DEBUG_FS` is off. This box
  builds `CONFIG_DEBUG_FS=y` (confirmed: `/boot/config-7.2.7-hyphaed`), so
  the bug is **dormant here today** — `cat /proc/sys/kernel/sched_itmt_enabled`
  already reads 1, ITMT already works. 2-line fix (`IS_ERR` instead of
  `IS_ERR_OR_NULL`, drop the early return), zero risk, defensive value only
  if `DEBUG_FS` is ever turned off for a future hardening pass on either
  machine. Per this repo's evidence gate, this has **no observable effect to
  measure today** — recorded as reviewed and not adopted into the series
  rather than manufactured into a patch with a fabricated "benefit."
  Revisit only if `DEBUG_FS` is ever disabled.

**Reviewed, rejected, reasons recorded:**

- `intel_pstate` HWP-init refactor (`db53c573d31d` "Fix setting minimum
  P-state at init time", `9e4cb21f2940` "Adjust policy->cur in active mode",
  and 9 more consolidation-only commits in the same series) — these are a
  connected refactor, not independently cherry-pickable; taking one without
  the rest risks intermediate states the authors never intended to ship.
  Would need the whole v7.3 `intel_pstate` series or none of it. Not worth
  the compile/measurement burden for a refactor with no reported bug on
  Raptor Lake specifically.
- `sched/cache` (`3cb0243767fd` and 5 more, LLC-affinity cache-aware
  scheduling): single-LLC box (36 MB shared L3, `numa_nodes=1`), this
  mechanism exists to keep related tasks on the *same* LLC across a
  multi-LLC/multi-socket topology. Nothing to optimize here, and it's new
  scheduler-core machinery interacting with `SCHED_BORE` in ways nobody has
  tested. Reject.
- `sched/eevdf: Move to a single runqueue` (`85570f10a4c6`) and the eevdf
  slice-protection series (7 commits): touches `kernel/sched/fair.c` deeply,
  the same file `SCHED_BORE` patches. BORE is a fork's own scheduling class
  layered on EEVDF internals; taking unrelated EEVDF restructuring without
  BORE's own upstream tracking that change first is exactly the class of
  hand-merge this repo's rules say to avoid (see the BBRv3 precedent, T9).
  Reject, revisit only if CachyOS/XanMod publish a 7.3-compatible BORE.
- Asym-capacity load-balance fixes (`7fd540b1bcaf`, `50b101f6e586`,
  `180ff97c1869`, `293f9611ae73`, `f2c2ba7219e5`) — checked
  `/sys/devices/system/cpu/cpu{0,16}/cpu_capacity`: both read **1024**. This
  box's P/E split is handled via ITMT priority (`SCHED_MC_PRIO`) and cluster
  topology (`SCHED_CLUSTER`), not `SD_ASYM_CPUCAPACITY` — these commits
  target big.LITTLE-style asymmetric-*capacity* domains, which this box's
  scheduler topology doesn't instantiate. Reject.
- `x86/topology: Add TOPO_CPU_TYPE_LOW_POWER` — AMD/Intel low-power E-core
  distinction work in progress upstream, not yet a complete usable feature
  (single commit, no consumer). Nothing to take yet.
- `PCI/P2PDMA: Add Nvidia Vera Rubin to whitelist` — datacenter GPU, not
  this box's Blackwell GeForce part. Not applicable.
- zram/zswap/mm-swap series (`mm, swap: fix SWAP_USAGE_OFFLIST_BIT
  collision`, `mm/zswap: support batch writeback`, `zram: switch to unsigned
  long indexing`, etc., ~25 commits) — real fixes, but for bugs nobody has
  reproduced on this box's zram/zswap config, and several are large enough
  (new `swap_ops.h` abstraction layer) that they're really a v7.3-cycle
  refactor rather than independently backportable fixes. Reject as a batch;
  the `SWAP_USAGE_OFFLIST_BIT` collision fix specifically is the one item
  worth a second look at the *next* bump if this box's zram accounting is
  ever suspected of drift.
- `dma-buf`/`dma-fence` fixes (`3ed11c671ff7`, `06dd5e1ae8ce`,
  `b344ca94e8cc`) — same subsystem as carried patches 0019/0020, but these
  fix `dma_fence` timeline-signaling and phys-vec-to-sgt overflow paths our
  patches don't touch (0019/0020 only add a priority hint and a compressed-
  descriptor field, no fence or sgt logic). No interaction, no need to
  carry — they'll arrive with the next ordinary kernel-org bump once they're
  in a stable release, no forward-port needed.
- `x86/build/64: Prevent native builds from generating EGPR use` — this box
  builds `CONFIG_X86_NATIVE_CPU=y` (`-march=native`-equivalent), which is
  exactly the build mode this commit's subject names. Read the diff: it's a
  `Kconfig`/Makefile guard against a **compiler bug class** (APX/EGPR
  register encoding reaching object code the bootloader/decompressor can't
  execute) that requires binutils/GCC versions newer than what's likely on
  either machine to even trigger. No reproducer, no observed miscompile.
  Recorded for the next GCC/binutils bump, not taken blind.

**No commits found** (0 in `v7.2..v7.3-rc5`): `r8169_main.c` — this box's
actual NIC driver has zero changes in this window. Nothing to do.

## Valve SteamOS kernel (`evlaV/linux-integration`) — nothing applicable

`gitlab.steamos.cloud/jupiter/linux-integration` (the official remote) timed
out repeatedly; `github.com/evlaV/linux-integration` is Valve's own GitHub
mirror and is reachable. Fetched `7.2/integration` (based on `7.2.7-valve1`)
plus the `endrift/7.2/xbox-gip` topic branch.

- **`7.2/integration` branch**: 200 most-recent non-merge commits triaged by
  author and Valve's own tag convention (`[FROM-UPSTREAM]`, `[NOT-FOR-
  UPSTREAM]`, `[FOR-UPSTREAM]`, `[FROM-ML]`). Overwhelmingly `wifi: rtw89`
  (Realtek 802.11 chips used in Steam Deck/handhelds — this box's Wi-Fi is
  Intel `iwlwifi`, zero overlap), AMD-specific work (`drm/amdgpu` soft-evict,
  `pinctrl-amd` Fremont GPP6 S4-wake, `asus-wmi`/`hid-oxp`/`hid-lenovo-go-s`
  handheld peripherals), and Intel `i915` cdclk cleanups (integrated-graphics
  only — this box runs `CONFIG_DRM_I915` disabled per
  `61-no-amdgpu-no-nouveau.config`'s sibling exclusion, discrete NVIDIA
  only). None of it touches this box's actual hardware surface (i9-14900KF
  desktop CPU, RTX 5070 discrete, r8169 Ethernet, `iwlwifi`). **Zero
  candidates.**
- **`endrift/7.2/xbox-gip`** (Vicki Pfau, `[FOR-UPSTREAM]`, 9 commits): a
  genuinely new driver, `xbox_gip`, implementing Microsoft's Gaming Input
  Protocol for Xbox controllers (USB and the official Xbox Wireless
  Adapter), replacing `xpad`'s existing Xbox One handling. Real and
  interesting, but out of scope here: it's still pre-upstream (not yet
  accepted anywhere), this box's Xbox controller path goes through
  **xpadneo** (Bluetooth, `hid-xpadneo` — see the `59-xpadneo-hidraw-
  preempt.rules` udev handling already in this repo), and adopting a new
  input driver needs a real controller test session this read-only audit
  can't perform. Not adopted; worth a look if a wired/USB Xbox controller or
  the official wireless dongle is ever introduced on this box.
- **`matts/7.0/upstream-low-latency-flip`**: not fetched (time-boxed out of
  this sweep after the two branches above returned nothing actionable). If
  chased later, check whether it's DRM-core (portable) or `amdgpu`-only
  (not applicable) before spending time on it.
- AMD-only branches (`pixelcluster/7.2/{drmexec,soft-evict-fix}` TTM
  eviction-priority work, `bob/7.2+hdmi-vrr`) — correctly out of scope per
  the plan's own gating (no AMD GPU active on either target machine; the
  laptop's Radeon 880M iGPU is a future concern, not this bump's).
- Handheld platform drivers (`oxpec`, `hid-lenovo-go`, `asus-wmi` allyx fan
  curves, `gos-brightness`, `panther-lake` fixes) — wrong hardware class
  entirely, rejected without a second look per the plan.

## Net result

One patch drafted and compile-checked (0030, boot-time PCIe retrain fix —
see `docs/tasks_patches.md` T21 and `patches/custom/0030-*`), one backport
reviewed and shelved as currently-inert (ITMT/debugfs, 0031-candidate), one
new driver noted for a future session with real controller hardware
(xbox_gip), and two negative results worth keeping so they aren't re-run
identically next bump (Ubuntu SAUCE is empty; SteamOS's 7.2 branch has no
Intel/NVIDIA-relevant content). No arXiv/GitHub/GitLab/NVIDIA-article sweep
was run this session beyond what the last three research docs already
covered — nothing published since 2026-09-10 was flagged as needing it.
